# gaderia_mobile_admin_back

API для мобільного застосунку Gaderia та адмін-панелі ([`nextjs-app-orders-front`](https://github.com/yuriivydai34/nextjs-app-orders-front)).

## Стек

- NestJS 11, TypeScript
- TypeORM + PostgreSQL (**на проді 12.x**, локально в розробці 16)
- JWT (`@nestjs/jwt` + passport), bcrypt для паролів
- `@nestjs/schedule` — щогодинна синхронізація з WooCommerce
- `xlsx` — звіти по замовленнях

## Змінні оточення

Файл `.env` у корені (у `.gitignore`, на сервері лежить свій):

```
DB_HOST=...
DB_PORT=5432
DB_USER=...
DB_PASSWORD=...
DB_NAME=...

PASSWORD_PEPPER=...        # додається до пароля перед bcrypt; без нього вхід зламається
JWT_SECRET=...             # без нього береться 'changeme'

# Імпорт покупців із сайту
WOO_URL=https://gaderia.com.ua/wp-json/wc/v3
WOO_CONSUMER_KEY=ck_...
WOO_CONSUMER_SECRET=cs_...
WOO_SYNC_CRON=on           # 'off' вимикає щогодинний синк, лишаючи ручний запуск
```

`WOO_URL` приймає і корінь сайту, і готовий шлях до API.

## Локальна розробка

```bash
npm install
docker compose up -d          # PostgreSQL на 55432 + Adminer на 8081
npm run build
node scripts/dev-db-init.mjs  # створити схему з сутностей TypeORM
npm run start:dev
```

`dev-db-init.mjs` працює тільки з локальним хостом: він використовує `synchronize`, який переписує схему під сутності, і на справжній базі це неприпустимо.

Щоб перевірити міграцію на реальному шляху оновлення:

```bash
node scripts/dev-db-init.mjs --as-prod   # прибрати те, що додає міграція
# далі накотити migrations/*.sql і подивитись, чи все стало на місце
```

## Схема бази

`synchronize: false` — схему не генерує ніхто. Кожна зміна це файл у `migrations/`, звичайний SQL.

**Чому SQL, а не міграції TypeORM.** Одну базу читають два проекти: ця адмінка через TypeORM і `app-server` через Sequelize (там теж немає ні міграцій, ні `sync()`). Інструмент, прив'язаний до однієї ORM, генерував би зміни з її моделей і вважав би оголошення другої сторони дрейфом. Чистий SQL — спільний знаменник.

Звідси правило: **одна зміна схеми = одна міграція + два оголошення** — сутність тут і модель у `app-server`. Забути одне з двох ловить `schema_check` на старті `app-server`: він звіряє моделі з базою й пише на пошту.

### Накатити

```bash
node scripts/migrate.mjs            # застосувати все незастосоване
node scripts/migrate.mjs --check    # лише показати, що чекає; нічого не змінює
node scripts/migrate.mjs --baseline # записати все як застосоване, не виконуючи
```

Застосоване лежить у таблиці `schema_migrations`. До появи раннера її не було, і дізнатись, чи накотили міграцію на прод, можна було тільки подивившись, чи є в базі той індекс.

**`.env` тут вказує на прод**, тому запис у нелокальну базу вимагає ще й `--remote`:

```bash
node scripts/migrate.mjs --remote
```

`--check` цього не потребує — він лише читає.

`--baseline` потрібен, коли схема вже актуальна, а записів немає: саме так виглядав прод, де 001–003 накотили руками. Записати їх правильно, а от виконувати 003 повторно означало б дарма переписати таблицю `account`.

Деплой виконує `node scripts/migrate.mjs --check` і **падає**, якщо щось не накочено. Накат лишається ручним — автоматика тут лише робить неможливим тихо забути.

Усі міграції написані так, щоб повторний запуск нічого не ламав. Раннер на це спирається: файл сам відкриває транзакцію й закриває її `COMMIT`, тож запис про успіх робиться одразу ПІСЛЯ неї, не всередині. Якщо процес помре між цими двома кроками, міграція лишиться незаписаною й виконається ще раз — нешкідливо саме завдяки ідемпотентності.

Накотити вручну, без раннера, теж можна:

```bash
psql -h "$DB_HOST" -U "$DB_USER" -d "$DB_NAME" -v ON_ERROR_STOP=1 \
  -f migrations/001_customer_import.sql
```

Перевірити стан схеми:

```bash
node scripts/check-schema.mjs
```

### Email як логін

Реєстрація та вхід ідуть за email, тож на `account` стоїть унікальний індекс по `lower(email)` (міграція 002). Саме індекс, а не перевірка в коді, вирішує: `register` спершу шукає адресу, але між пошуком і вставкою може прослизнути друга реєстрація — порушення унікальності перехоплюється й перетворюється на `409`.

Адреси зберігаються в нижньому регістрі, а `findByEmail` шукає без урахування регістру, тож `Ivan@x.com` і `ivan@x.com` — це один акаунт. Те саме стосується редагування з адмінки: спроба вписати зайняту адресу дає `409`, а не 500.

### `account` і `customer` — це різні речі

- **`account`** — акаунти застосунку: логін, пароль, роль. Сюди пишуть `register` і `login`.
- **`customer`** — покупці, імпортовані з сайту. Довідник контактів **без пароля й без входу**.

Їх навмисно не змішано. Якби імпортовані люди потрапили в `account`, ті з них, хто має email, не змогли б ані зареєструватись (`register` відповідає «Email already in use»), ані увійти (`login` відхиляє запис без пароля).

## Часті операції

### Змінити пароль користувача

В API скидання пароля немає — тільки `register` і `login`. Вписати хеш у базу руками теж не вийде: пароль зберігається як `bcrypt(пароль + PASSWORD_PEPPER)`.

```bash
node scripts/set-password.mjs someone@example.com
```

Запитає пароль двічі без відображення на екрані, тож він не потрапить ні в історію команд, ні в список процесів. Для скриптів можна подати через `stdin`:

```bash
echo 'новий-пароль' | node scripts/set-password.mjs someone@example.com
```

Після запису скрипт перечитує збережений хеш і перевіряє, що пароль до нього підходить. Відмовиться працювати, якщо немає `PASSWORD_PEPPER`, адреси немає в базі, пароль коротший за 8 символів, або під однією адресою знайшлось кілька акаунтів (після міграції 002 це не має траплятись, але перевірка лишається).

### Синхронізація покупців із сайту

```bash
node scripts/woo-sync.mjs           # інкрементально, від збереженого курсора
node scripts/woo-sync.mjs --full    # ігнорувати курсор і перечитати все
```

Те саме робить щогодинний cron і кнопка «Синхронізувати сайт» в адмінці (`POST /integrations/woocommerce/sync`).

Повний прогін — близько 17 тисяч замовлень, ~3.5 хвилини, пік пам'яті ~45 МБ (читання йде посторінково).

### Подивитись, що насправді віддає магазин

```bash
node scripts/woo-probe.mjs
```

Нічого не змінює. Показує, які параметри приймає сайт, як виглядає `billing`, скільки замовлень мають email і телефон, які значення в `billing.state` і які ключі `meta_data` додали плагіни. Варто запускати перед будь-якою правкою мапінгу — дані магазину змінюються з часом.

## Як влаштований імпорт з WooCommerce

Усі замовлення в магазині — гостьові (`customer_id: 0`), клієнтських записів у Woo немає. Люди дістаються з блоку `billing` у замовленнях.

- **Ключ ідентифікації — телефон** (є у 100% замовлень), email лише як запасний (є у ~69%).
- Об'єднання «спільний телефон **або** спільний email» пробували й відкинули: один службовий email стягнув 52 різні людини в одну групу.
- Адреса береться з `billing`, а якщо там порожньо — з `shipping`. Це не дрібниця: у `billing` адреса є лише у 37% випадків, бо відділення Нової Пошти лежить у `shipping`.
- Плоскі колонки йдуть за найсвіжішим замовленням, а `source_data` (jsonb) зберігає **всю** історію: кожен email і телефон із датами першої й останньої появи, усі варіанти імені та адреси, по батькові з мета-полів, дані доставки з ТТН, коментарі й перелік замовлень.
- Інкрементальний прогін **зливає** нове зі збереженим, а не перезаписує: у його вікно потрапляють лише свіжі замовлення, і без злиття історія людини стерлася б.
- Курсор у `integration_state` рухається лише після успішного прогону й зсувається на секунду назад, бо `modified_after` у Woo виключний. Перечитати замовлення безпечно, пропустити — ні.

Пошук по `/customers` заглядає і в `source_data`, тож людину знайде за адресою чи email, який вона вводила один раз.

## Деплой

Автоматично при push у `main` — [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml): збірка, `scp` на сервер, `npm ci --omit=dev`, `pm2 restart`.

На сервер копіюються `dist/`, `migrations/`, `scripts/`, `package.json`, `package-lock.json`.

> `package.json` у цьому списку — не для порядку. Раніше їхав лише `dist/`, тож `npm ci` ставив залежності зі старого файлу на сервері. Коли в коміті з'явилась нова залежність, застосунок не зміг стартувати й пролежав годину, хоча GitHub Actions показував зелений статус: `npm ci` і `pm2 restart` відпрацювали без помилки, а падіння сталося вже після них.

Тому після деплою варто дивитись не лише на статус воркфлоу:

```bash
pm2 list                    # має бути online, а не errored
pm2 logs <name> --lines 50
```

Секрети репозиторію: `SSH_HOST`, `SSH_PORT`, `SSH_USER`, `SSH_PRIVATE_KEY`, `APP_PATH`, `PM2_APP_NAME`.

## Відоме

- **PostgreSQL 12 на проді** — давно поза підтримкою.
- **Замовлення з сайту не імпортуються**, тільки люди. У замовлень, створених мобільним застосунком, у Woo є `_app_payment_id` — посилання на `payment.id`, за яким їх можна зіставляти, а не дублювати.
- **На кожен push запускається два однакових деплої** — схоже на дубльований тригер, варто перевірити налаштування репозиторію.
